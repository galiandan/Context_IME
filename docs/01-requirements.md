# 01 · 需求与验收

## 1. 产品目标与术语

目标是在编程语言的字符串内容与代码之间自动应用用户的输入方案。文本方案可为中文、日文或任何已配置输入源，不在平台接口中写死中文。

**上下文**是 `code / string / comment / unknown`；**策略**是 `code / text / keep`；**输入方案**是用户为 code 和 text 选择的具体系统源及可选受支持模式。这三层不能混用。默认映射：code → code，string → text，comment → code，unknown → keep。unknown 的映射不可改成强制切换。

第一版面向桌面 Windows、macOS、Linux；优先完成 Python、JavaScript、TypeScript、C、C++。不能可靠识别的语言或局部结构保持现状。JSX/TSX、Markdown、Notebook、终端、搜索框、Git 提交输入框、Vim 模式适配均不在首版范围。

不做 AI/云端判断，不上传代码，不扫描工作区文件。只在本地读取必要的打开文档行用于识别；不记录代码、候选词或输入文本。不修改代码、不替换标点、不注入 VS Code、不调用未公开命令。

## 2. 插入位置契约

`|` 是测试中的光标，不属于真实内容。识别下一次插入的位置，不简单取左右字符的 token。

| 场景 | 上下文 | 默认策略 |
| --- | --- | --- |
| `print(\|"hello")` | code | code |
| `print("\|")` | string | text |
| `print("hello\|")` | string | text |
| `print("hello"\|)` | code | code |
| `print("\|` | string，尚未闭合 | text |
| `print("a\"b\|")` | string，转义未闭合外层 | text |
| `# "文本\|"`（Python） | comment | code |
| `// "文本\|"`（JS/C 等） | comment | code |
| `#\|include <stdio.h>`（C/C++） | code | code |
| `'x\|'`（C/C++） | code，字符字面量 | code |
| `“\|文本”` | 不能因弯引号判为 string | 可靠 code 则 code，否则 keep |

完整开分隔符之后进入字符串内容，闭分隔符之前仍在字符串内容，完整闭合之后回到外层上下文。多字符定界符内部无法可靠判断时 unknown。字符串内中文弯引号只是内容，不产生新边界。

必须覆盖 Python 单双引号、三引号、raw string、f-string 文本/表达式/嵌套字符串；JS/TS 模板文本、`${...}` 表达式、嵌套字符串及正则；C/C++ 字符与字符串区别；C++ raw string。Python docstring 仍按字符串处理，不因用途像注释就换类型。

行注释延续到行末插入位置，下一行按语言规则重判；块注释闭合后回到外层。C/C++ 续行等语法遵守 grammar 与已测试语言规则。

## 3. 用户行为

首次配置选择或记录 code/text 两个输入方案，不猜系统默认输入源。配置期间暂停自动规则，成功保存后等待有效编辑器交互；缺少方案显示“待配置”。退出字符串是应用 code 策略，不是恢复任意历史输入源。

同一区域内用户手动切换后，后续输入和移动不重复强制设置；下一次真正跨上下文边界或显式“重新同步”才重新应用。版本变化和区域位置偏移不是跨边界。无后端变更通知时不轮询，无法即时获知手动切换是明确限制。

多光标或非空选区默认暂停；折叠为单光标后，在有效编辑器交互中重新判定。窗口失焦、禁用或编辑器变化时清除待执行操作；失焦/停用不恢复输入法，以免影响其他应用。

## 4. 完成标准

验收必须覆盖字符串进出、注释三种策略、复杂语法、编辑缓存更新、候选词输入、手动覆盖和真实平台设置。平台能力按[四级兼容性表](04-platforms.md)报告；Mock 测试仅验证核心逻辑。

首版工程交付应包含源码、锁文件、F5 调试、检查与测试脚本、离线 grammar/WASM、helper 源码与构建脚本、平台 CI、VSIX、中文说明及许可证。实际实现与尚未完成的验证见 delivery.md 和 compatibility.md。
