# 11 · 行级增量缓存与工作预算

本文件定义增量算法，避免把“调用了 TextMate”或“做了防抖”当作增量实现。

## 1. 数据模型

每个文档以 URI、languageId、grammar 版本管理缓存，维护文档版本、已验证前缀/区间、脏区间、旧到新行映射、region 锚点和访问时间。行记录包含有限的原行文本或可靠修订身份、行首 StateStack、tokens、行尾 StateStack、是否完整和近似内存大小。

未修改的有效缓存可以跨文档版本保留，不能要求每行版本号等于新文档版本才可复用。`StateStack.equals` 用于语义状态比较，不依赖对象引用相同。初始从文件起点的 INITIAL 或已有可信检查点开始，不能在任意附近行假设 code。

## 2. 未修改时查询

光标行已有效则直接查 token/边界，不重新分词全文；需要局部边界探测时只处理当前行。行状态有效但 tokens 被淘汰时从该行已知入口重建一行。

光标位于未分析后缀时，从最近可信检查点顺序推进到目标行，不扫描目标之后的无关全文。不调用整份 `document.getText()`；按需获取 `lineAt` 文本。无有效入口时保持输入法，分批计算。

## 3. 文本修改与行号映射

文档变更事件内的 edits 按其所属旧快照统一解释，不能一边套用一个 edit、一边把下一个旧坐标当新坐标。第一步记录旧范围、替换文本换行数与长度；排序/归一化并建立分段坐标映射。

保留最早受影响行之前的有效前缀。被替换覆盖的行及与其拼接的首尾边界行标脏；仅由插删行导致位置变化、内容未改变的完整行映射到新行号，保存为**待验证后缀**，而不是立即作废或立即视为可靠。

例如旧第 10 行前插入两行，旧第 10 行后的完整行可映射为新行 +2；删除跨行范围会让原两端合并，合并行必须重新分词。多处编辑之间的未修改片段保留映射与状态，但只有传播收敛后才能直接查询。

文档版本连续性中断、事件范围不一致、语言/grammar 改变或真正全量替换时允许重建，并记录原因；普通单行编辑、插删行和多处编辑不得每次丢弃整个缓存。

## 4. 传播与收敛条件

从最早脏行之前的有效行尾状态推进。遇到一个新行与旧后缀映射对齐时，只有下列条件成立才复用：

1. 同一 grammar 版本；该行完整文本已通过编辑映射证明未变，或精确文本比较确认相同（仅 hash 相同不足以证明）。
2. 新输入状态与旧行首 StateStack 相等，旧行分词完整，才能直接复用该行 token 与行尾状态。
3. 若输入状态不同则重新分词；完整的新行尾状态与旧对应行尾状态相等后，可从下一行开始复用未修改连续区间。
4. 跨到后续另一处编辑时必须再次分词，不能因前一段已收敛就跳过后面的脏区。

相同文本行不能单独作为收敛依据：文件前部三引号被删除时，后面文本完全没变，词法状态却可能改变到文件尾部。首次修改后只推进到当前光标所需位置，其余后缀保持待验证，未来查询再推进。

## 5. 预算、让出与取消

每批最多处理 128 行或约 4ms，先达到者让出事件循环；每行传入初始 5ms 分词 timeLimit。一次光标请求累计分词墙钟预算初始 100ms，超出返回 unknown，保留已经完成的可信检查点，不无限后台重试。0.1.4 对 tokenizer-timeout 最多额外重试一次，先让出并重验剩余预算和取消条件；所有行和插入探测共享此配额。具体阈值以[性能文档](07-performance.md)为准。

每批开始/结束检查 generation、文档版本、焦点与启用状态。期间有新编辑则取消旧传播，基于新映射重排，不提交旧 tokens。窗口失焦停止后续批次；重获焦点不自动续扫，等待有效交互。

单行 > 20000 UTF-16 单位默认 unknown；该行未完成会阻断依赖它的后续状态，不能绕过它猜测。文件超配置大小直接暂停自动识别。超时行不保留为可信结果。

## 6. 内存与释放

初始最多 3 个最近文档、估算缓存总量 8MiB；超过限制先淘汰远处 tokens，再淘汰文档/检查点。估算上限不是 JS 堆精确硬上限，还需实际堆测量。scope 字符串与不可变 StateStack 尽可能共享，不保存全文副本。

淘汰关键入口后依赖它的未验证区间不能标记有效。文档关闭清除缓存、映射和锚点；扩展停用全部释放。已加载 grammar/WASM 单独计量，不能伪装成文档缓存内存。

## 7. 验证方式

测试固定多行样例，加确定随机种子的 insert/delete/replace 序列；每一步与从头分词基线比较结果和最终状态。另断言分词调用次数：暖缓存移动零次常规行分词、普通改动保留前缀、收敛后复用映射后缀、多处 edit 不漏掉后方脏区。

加入前部多行定界符修改、插删空行、CRLF、Unicode、自动补齐、粘贴、撤销重做、取消批次、缓存淘汰和反复打开关闭。通过结果正确性和工作量两个维度证明“真正增量”。

## 0.1.4 实现说明

普通单行编辑（包括同一事件多个不增删行的范围）只删除受影响行，不重建全部 Map。分类结果按实际访问过的行失效并准确扣除内存；插删行继续按旧快照重映射。达到 8MiB 时拒绝新增超限行，保留可信前缀和行尾状态，旧位置仍可查询，不再整份清空并永久阻塞。远处 token 淘汰与稀疏检查点重建尚未实现，超出容量的后缀仍返回 unknown。

生产仍使用 5ms 单行/插入探测、100ms 请求预算。语义测试显式关闭时间预算以隔离 CI 调度和正则懒编译噪声；独立预算测试校验默认参数、stoppedEarly、不可靠前驱、内存上限及前缀保留。性能 benchmark 使用生产默认预算，照实统计 unknown。

## 0.1.5 优化

区域定位先检查 token 是否包含起始标记，再检查 kind 与完整嵌套 scope 路径；不改变区域判定和锚点映射。位置结果 Map 仅在实际缓存光标查询时分配，编辑失效时释放；每行固定开销的保守估算仍为 256 字节，不因减少实际分配而扩大缓存容量。长区域仍线性回溯，稀疏检查点/远处 token 淘汰仍未实现。

## 0.1.6：token 淘汰与冷初始化

容量压力下按最近访问顺序压缩完整行，释放 text、普通 tokens 和位置结果；保留 input/output StateStack 及可能的区域起始 token。完整行固定估算 256 字节，压缩行 192 字节，token 仍按 160 字节另计；整体仍受 8MiB 估算约束，不是精确堆硬上限。再次访问压缩行仅从其可信 input 重分词该行，并验证 output 相等；stoppedEarly/状态冲突返回 unknown。保留起始 token 可维持跨已淘汰文本的区域身份，不能把无法找到起点的长字符串一律归入同一区域。

压缩行不保存原文：仅依赖完整编辑事件映射证明其文本未变，传播时还必须比较 input.equals。所有触及编辑范围的行均删除；插删行按旧快照统一重映射。收到不连续版本或 query 发现版本未报送时清空并从 INITIAL 重建。仍逐行保留状态，并未实现稀疏检查点；当状态/起始 token 本身耗尽预算时继续 unknown。大文件首次传播可能需多次有效交互，每次保留已完成前缀，不无限后台重试。

通过 Registry 的公开 createOnigScanner 工厂记录成功创建计数。通常最多一次重试；仅在当前超时尝试创建了新 scanner 时允许追加，总计最多三次重试，由常规行、被淘汰行恢复和插入探测共享。每次先 setImmediate 让出，再验证 generation/版本/焦点与剩余 100ms 请求预算；传给 tokenizeLine 的 5ms 不变。计数是初始化进展线索，不是对输入病态性的证明；单次同步正则仍不可抢占。区域回溯也按批检查预算并必要时让出。

测试与实际数据见 [0.1.6 报告](0.1.6-cache-cold.md)。
