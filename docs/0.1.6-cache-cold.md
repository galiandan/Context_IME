# 0.1.6 大文件与首次初始化优化

2026-09-27，本地实现、验证和打包，未发布 Marketplace，未修改系统输入法。运行环境：Linux 7.2.7-zen1-1-zen x64、AMD Ryzen 7 9700X、Node 26.10.0；VS Code 集成宿主 1.139.1。无新依赖，TextMate 9.2.0 / Oniguruma 2.0.1 / grammar 均保持原版本。

## 实现

缓存达到容量压力时，淘汰较旧行的原文、普通 token 和光标分类 Map，保留可信 input/output StateStack 与区域起始 token。再次访问只恢复目标行，并核验输出状态；区域起点仍可跨越被淘汰行查找，防止手动输入法覆盖因区域身份变化被抢回。压缩行依靠完整修改事件映射证明文本未变，还须输入状态相等才复用；版本断档则安全重建。

上限仍为 8MiB 估算值：完整行基本开销 256 字节、压缩行 192 字节，文本、token、结果和锚点另计。压缩行已移出完整行访问集合并释放主要负载，减少估算对应实际结构变化，不是单纯提高上限。状态仍逐行保存，不是稀疏检查点算法，极大文件或大量起始 token 仍可能 cache-limit。

冷初始化通过公开 Registry createOnigScanner 工厂记录 scanner 成功创建计数。保留原先的一次重试；只有本次超时调用创建了新 scanner，才继续追加，总计每请求最多三次，由行分词、淘汰行恢复与插入探测共享。每次让出事件循环并重验取消/版本/100ms 截止时间，传入的单次 5ms 不变；不预加载所有语言、不忽略 stoppedEarly、不增加后台轮询。

源码核实：TextMate 的 [v9.2.0 tokenizeString](https://github.com/microsoft/vscode-textmate/blob/f0f2a44b4c055b0e0fa3869e5de338efda5b7cf1/src/grammar/tokenizeString.ts) 在同步扫描之间检查 elapsedTime，不能抢占单次正则；[rule.ts](https://github.com/microsoft/vscode-textmate/blob/f0f2a44b4c055b0e0fa3869e5de338efda5b7cf1/src/rule.ts) 通过 scanner 工厂构建规则扫描器；[Oniguruma v2.0.1](https://github.com/microsoft/vscode-oniguruma/blob/184a6e2d4603c5a31efc0a33f544be1545d9ec6b/src/index.ts) 在构造 scanner 时调用 WASM 创建函数。因此 scanner 创建计数可用作初始化进展线索，但不是严格的“非病态输入”证明；总次数与时间预算始终保留。

上游 tag 对应 commit 已用 git ls-remote 核实：TextMate `f0f2a44b4c055b0e0fa3869e5de338efda5b7cf1`、Oniguruma `184a6e2d4603c5a31efc0a33f544be1545d9ec6b`。

## 大文件实测

两版都使用相同 esbuild CJS 打包、Node --expose-gc、同一合成 fixture。基线来自本轮开始时 0.1.5 工作树，优化为 0.1.6；无实际 IME set。准备阶段先分批分析到尾部，再统计交互；每个移动/输入场景 1000 次，head-edit 100 次。原始 JSON 见 [数据目录](benchmarks/perf-0.1.6)。

| 场景 | 0.1.5 unknown | 0.1.6 unknown | 新 p50 ms | 新 p95 ms | 新 CPU 合计 ms |
|---|---:|---:|---:|---:|---:|
| python-simple-10k-type | 0/1000 | 0/1000 | 0.261 | 0.720 | 300.2 |
| python-code-10k-move | 226/1000 | 0/1000 | 0.012 | 0.025 | 17.9 |
| python-multiline-10k-move | 0/1000 | 0/1000 | 0.218 | 0.396 | 268.2 |
| python-code-10k-type | 1000/1000 | 0/1000 | 0.300 | 0.787 | 350.5 |
| python-multiline-10k-type | 0/1000 | 0/1000 | 0.408 | 0.450 | 465.3 |
| python-code-10k-head-edit | 100/100 | 0/100 | 5.584 | 5.999 | 597.5 |
| python-multiline-10k-head-edit | 0/100 | 0/100 | 1.388 | 1.905 | 201.9 |
| cpp-comment-10k-move | 0/1000 | 0/1000 | 0.217 | 0.393 | 266.6 |
| js-template-10k-move | 0/1000 | 0/1000 | 0.262 | 0.480 | 315.2 |
| python-code-40k-move | 805/1000 | 0/1000 | 0.019 | 0.024 | 35.5 |

旧版 code-10k 末尾输入/前部修改全为 cache-limit，四万行移动 805/1000 unknown；新版以上场景全部正确返回 code。旧版快速 unknown 不能作为延迟优势。五语言小文件的分类计数保持一致，其中 JS/TS/C++ 多字符定界符内部仍有预期的 ambiguous-boundary。

大文件**首次分析仍有成本**（首轮最终代码准备数据）：本轮 code-10k 准备为 1–2 次请求、约 95–105ms；code-40k 为 4 次请求、约 372ms，不能把暖查询 0.023ms 宣称为首次打开延迟。基准显式跟进请求，生产需下一次有效编辑器交互，不会无限后台重试。前部修改需要传播到一万行尾部，成功分类的 p95 约 6.00ms，高于 5ms 增量目标；后续可进一步优化收敛区间跳过，但不能以忽略未验证后缀替代。

首轮四万行场景准备后测试进程 heapUsed 从 28.63MiB 到 24.56MiB，同时覆盖行数增加；一万行完整缓存小幅增加约 0.1–0.3MiB。100 次打开/关闭缓存归零，GC 后 heapUsed 约 16.48–16.57MiB，无持续线性增长迹象。整个压力进程峰值 RSS 约 545.6MiB（基线约 544.7MiB），包含 Node/V8/WASM、夹具和瞬时分配，不是扩展常驻独占内存；不能将 8MiB 估算上限解释成实际进程上限。

## 冷启动对照

每语言、每版本各 30 个全新 Node 进程，共 300 个。统计 grammar/WASM 加载加 100 行首次查询；不计 Node 进程启动及 GC。原版跟进查询累计耗时不含用户等待下一次交互的时间。

| 语言 | 原首次 unknown | 新首次 unknown | 原首次 p95 ms | 原至可分类累计 p95 ms | 新首次完成 p95 ms |
|---|---:|---:|---:|---:|---:|
| python | 0/30 | 0/30 | 48.96 | 48.96 | 49.92 |
| javascript | 30/30 | 0/30 | 58.36 | 74.49 | 77.66 |
| typescript | 30/30 | 0/30 | 58.54 | 74.57 | 79.36 |
| c | 0/30 | 0/30 | 50.39 | 50.39 | 53.81 |
| cpp | 30/30 | 0/30 | 84.98 | 102.64 | 101.19 |

改进是消除本机这些样本的“必须等下一次输入才能分类”，不是减少 regex 本身编译成本。JS/TS 首次请求更长，因为本次请求完成了原本下一次交互才做的工作。C++ 总时长含 grammar/WASM 加载，因此可超过 DocumentCache 内部 100ms 预算。换机器、未见过的语法或系统繁忙时仍可能 unknown，不保证所有冷启动永不超时。
